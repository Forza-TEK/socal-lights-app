## A. Contest integrity detail

**1. Vote integrity (mostly good).**
- Uniqueness: `INSERT ... ON CONFLICT(contest_id,user_id,category) DO UPDATE` (`vote.js:255`) means two simultaneous requests cannot create two rows. Confirmed by code; the UNIQUE index lives in the migration (`0109`, not re-read).
- Blocks: signed-in required (`requireUser`), same-origin check, contest `live`, window open, own-home block (`vote.js:252`), judges blocked from the public vote (`:246`), category must be one of the contest's, home must be approved in the contest. Vote moves are allowed until close. After announce the window is closed (`windows` requires `!announced`) so votes cannot change.
- Not enforced: organizer/staff voting or entering (C11), Turnstile on votes, IP or device signals (C10).
- Voiding exists and is locked after announce, but is unlogged (C6).
- Race: entry limit (5 per account) and per-IP throttle are check-then-insert, so small overshoot is possible (Low, not ranked).

**2. Judge flows.** Invitation is by email match, not by token (judges sign in with the invited address; `judgeOf` uses `email = user.email`, both normalized, `judges.js:58`). Own home blocked (`judge.js:54`, `judging.js:271`). Scoring: integer 1 to 10, trimmed mean only at 5+ scores for a home (`contests.js:94-98`), conflicted judges' rows excluded in `computeResults`. Ties: share the win; public ties broken by judges only in mode `both`. Leakage: judge picks/scores appear to the organizer and co-organizers live during voting (`[slug].js:38`), judge identities are not tied to scores in the public view; after announce only aggregates are exposed. Organizer seeing live scores can pressure judges (accepted design, but note it). See C18.

**3. Freeze and publication.** Results hidden until announced unless `show_counts` (`[slug].js:23`). Snapshot stores categories, winners, awards, per-entry votes and judge values, dq flag; it does not store voided counts, judge-conflict exclusions, or who announced (only the generic change log row). Export CSV contains contest name, entry name and address, counts, awards, prize, flag. No emails or voter data, formula-injection defused (`export.js:209`). Emails: `results_winner`/`results_entrant`, cap 200, silent failures (C13). Crowns/badges follow the snapshot (not re-read in detail). Re-opening after announce is impossible through the API (all mutators check `announced` except C3); Admin can only delete or decline the contest.

**4. Organizer and entrant safeguards.**
- Creation limit 3 per account per 24 h (`index.js:206`); entries 5 per account per contest, 60 per IP per hour for contests (`submit.js:49,81`). No limit on total contests across many accounts, no Turnstile (accounts replace it).
- The "free-mail goes live immediately" change is confirmed (`index.js:210` sets `live = true`; the `pending` branch is dead code). The note text is `email is a free-mail address`, `given with no website`, or `does not match the website`. Admin tooling: contests tab lists `c.*` including `note` (`admin/contests/index.js`), supports `decline` (unlists the map event, emails the owner, `contest_unpublished`), `approve`, `edit`, and `DELETE` (full purge). So takedown exists and works; detection and notification do not (C1). Entrants and voters on a declined contest cannot act (status checks), but entrants can still PATCH their entry text (`mine.js` does not check status).
- Photo moderation: manual approval keeps photos in `pending/`; `auto` approval publishes immediately with no moderation. Entry decline emails the entrant with a reason.
- Sponsor and prize fields: free text, sniffed image logos (JPG/PNG/WebP, 600 KB), up to 12 sponsors; URLs go through `webUrl`. Pages escape output with `esc` (`shell.js:3`); `contest.html` uses `esc` for rules text.
- Past pages and privacy scrub: reviewed, sound (`archive.js`), see C19.

**5. Payment and Featured.** Clean separation confirmed (C14). `_lib/featured.js` is only referenced by checkout, config, admin and the webhook.

**8. Observability.** Logging is almost absent: 3 `console.error` calls in `functions/` and many `catch {}` (for example `notifyResults`, `tell`, `judgeOf`, `computeResults` judge block). The Stripe webhook returns 500 on failure so Stripe retries and emails the account owner (Stripe-side, not verified). There is a "Submission digest" email three times a day (a proxy heartbeat for the site: if it stops arriving, something is wrong) and an Admin dashboard (`admin/dashboard.js`) with counts and a log (`adminlog.js`), but no error, email-failure or job-health panel. No `[observability]` in `wrangler.toml`; Cloudflare Logpush availability on the free plan was not verified. No uptime monitoring in repo or docs (none found). Cheapest setup: (1) add `[observability] enabled = true` to `wrangler.toml` (Workers Logs, free tier) and replace `catch {}` with `console.error` plus an `error_log` D1 table surfaced in Admin; (2) a free UptimeRobot or Better Stack monitor on `https://socallights.app/api/config` and the pages.dev address, alerting to email and phone; (3) a Cloudflare Notification for Pages deployment failure and Workers error spike; (4) turn the digest into a dead-man check by adding to its email "emails failed last 24 h" and "last migration run"; (5) make each cron workflow open a GitHub issue on failure.

## Verified OK

- DB-enforced one vote per person per category, with upsert and conflict handling safe under concurrent requests (`vote.js:255`).
- Voting and entry windows are checked server-side; paused flags work; no votes after announce.
- Own-home block for voters and judges; judges barred from the public ballot; judge recusals excluded from scoring.
- Trimmed mean at 5+ and tie-sharing logic match the published rules; public tie goes to judges in `both` mode.
- Results frozen into `contests.results` and read from there by contest page, archive, `/past` and export; hidden counts default respected in `GET [slug]`.
- CSV export contains no emails and defuses formula cells; voter emails are limited to organizer views (disclosed in privacy policy per `docs/rules-review.md`).
- Admin tooling can decline, edit and delete a contest, and Admin routes sit behind Access plus signed-JWT verification (documented; middleware not re-read).
- Output escaping on contest and past pages (`esc`), same-origin checks on mutations, SameSite cookies, hashed session tokens.
- Featured/plan code is kept out of contest queries and ordering; `upsertEvent` leaves featured columns alone.
- Migrations are gated (validate before apply, concurrency group, secret check), and migration runs have been green recently.
- `npm audit --omit=dev`: 0 vulnerabilities.
