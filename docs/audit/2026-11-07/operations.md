## Top 5

1. **The "every 15 minutes" uptime check does not run every 15 minutes (High).** GitHub ran it 6 times in 40 hours, gaps of 6 to 8 hours. The submission digest ran twice a day instead of three, and the first scheduled nightly backup was an hour late and absent when checked. Every alert in the repo depends on GitHub cron, which is best effort. An outage can go unnoticed for most of a day.
2. **Every nightly backup run prints a signed download link to a full database export in a public workflow log (High).** The link is valid for one hour. The file holds users, sessions, emails and orders. The repo is public.
3. **Pages deployments hang and nothing detects it (High).** Three incidents in 5 days: a production deploy "active" forever since Nov 2, a 41 to 73 minute stall on Nov 3, and a 36 minute stall tonight that left 8 production builds "skipped". Builds run one at a time, so one hang blocks every merge and every sweep.
4. **Preview deployments still use the production database and photo bucket (High).** The Cloudflare API shows the preview bindings point at production, which contradicts `docs/CHECKLIST.md`. Previews have no `TURNSTILE_SECRET`, and Turnstile fails open when it is missing, so a preview URL accepts unchecked writes into the live database. 79 previews were built in the last 24 hours.
5. **The home page `/` is an uncached Function that scans the events table twice per request (High if the account is on the free plan, otherwise Medium).** Measured: 4,618 D1 rows read per hit. D1 read 1.3M to 3.3M rows a day over the last 6 days with only about 25 human map views a day, so crawlers dominate. Today it was already at 3.29M by 11:00 UTC. The free cap is 5M a day. The CPU numbers suggest the account is on Workers Paid, but that is not confirmed.

## Ranked findings

### High

**H1. Scheduled GitHub workflows are unreliable, and every alert depends on them**
- Evidence: `Uptime check` scheduled runs (declared `*/15`): 2026-11-05 00:24, 07:16, 15:44, 21:36, 2026-11-06 01:49, 09:13. Six runs in about 40 hours. `Submission digest` (declared 03:00, 15:00, 21:00): runs at about 10:25 and 21:00 each day, two a day. `Nightly backup` (declared 10:17): zero scheduled runs so far (3 manual runs only); at 11:15 the 10:17 run had not appeared.
- Impact: the uptime check, the backup, the digest, contest reminders and the weekly email all use GitHub cron. GitHub documents scheduled runs as best effort and delayed or dropped under load. The statement in `docs/CHECKLIST.md` and `docs/status.md` that the site is checked every 15 minutes is not true. A real outage, or a missed backup, can go unnoticed for 6 to 12 hours. Nothing tells the owner that a workflow did not run.
- Fix: add a monitor that does not live on GitHub. Free options: UptimeRobot or Better Stack (1 to 5 minute interval, email and push) on `https://socallights.app/api/config` and `/api/events`; and a dead-man's-switch (healthchecks.io free) that the backup workflow pings on success, so a missing backup raises an alert. Keep the GitHub check as a second layer. Change the docs to say "best effort".
- Effort: S.

**H2. Backup workflow leaks a signed link to the full database export into public logs**
- Evidence: log of run 42157160976 (`Nightly backup`, step "Export the live database"), line 204: wrangler prints "You can also download your export from the following URL manually. This link will be valid for one hour: https://...r2.cloudflarestorage.com/d1-sqlio-outgoing-prod/<db id>-....sql?X-Amz-...&X-Amz-Signature=...". The repository is public (`private:false`). The workflow's own header says the backup must never be public because "it contains emails".
- Impact: anyone who can read the run log within the hour (GitHub shows logs of public repos to any signed-in user; the API gives them to any token) can download the whole database: 5 users and their emails, sessions, login codes, orders, claims, leads, the admin log. The link in the run I read has already expired. A new one is printed every night.
- Fix: do not use the `wrangler d1 export` console output. Either pipe it through a filter (`npx wrangler d1 export ... 2>&1 | sed -E 's#https://[^ ]*cloudflarestorage[^ ]*#<link hidden>#'`) or call the D1 export REST endpoint with `curl --silent` and fetch the link without printing it. Add `::add-mask::` for the link if it can be captured. Treat sessions as exposed only if a link was ever fetched; there is no evidence of that.
- Effort: S.

**M8. Caching failure modes of `/api/events`**
- Evidence: `functions/api/events.js`. The Cache API copy is per data center, so each busy colo rebuilds every 2 minutes from live D1 (3,270 rows read per rebuild, up to 2.4M rows a day per colo). `cf-cache-status` stays DYNAMIC so the Function runs on every request (the saving is D1 reads, not invocations). A stale copy is served up to 15 minutes; there is no purge, so an unpublished or cancelled event can stay visible for 15 minutes on a quiet colo. Several requests arriving in the stale window each start a rebuild (no lock). A failed background rebuild is swallowed (`.catch(() => {})`), then the next request after `KEEP_S` builds inline and returns 500 with nothing logged. A failure in `approvedPosts` is swallowed, which quietly shows events a home post should hide. `/api/events/<id>` details are `no-store` for misses and not otherwise cached (live read: 404 with `cache-control: no-store`). The `ETag` and 304 path works (live response carries `etag`, `cache-control: public, max-age=60, s-maxage=120`; 135,489 bytes gzip, down from 314,439 on Nov 4).
- Impact: bounded and acceptable at today's traffic; the failure modes are silent.
- Fix: log a `logOp` on rebuild failure; add `waitUntil` single-flight with a short lock key; document the 15 minute staleness for takedowns (or call `cache.delete` from the admin event actions, which only clears the colo that handled it).
- Effort: S.

**M9. Quotas shared by everything, and one unthrottled paid-key proxy**
- Evidence: Resend (free plan: 100 emails a day, 3,000 a month, if that is the plan) is the single sender for sign-in codes, order and claim emails, the 3 a day digest, the weekly email (20 per batch up to 30 batches), contest reminders and invites. Per-account caps exist (`functions/_lib/sendlimit.js`: 100 a day per account) but nothing budgets the total. `GET /api/address` (Geoapify, free 3,000 credits a day) is unauthenticated with no rate limit; each new query of 5+ characters with a digit spends a credit (responses are cached 24 h per identical query). Geocoding of submissions uses the US Census geocoder first, then Nominatim with a User-Agent and 4 s timeout, once per submission (policy: 1 request a second, identifying agent; compliant at this volume). `docs/sweep-methods.md` uses Nominatim at 1 a second.
- Impact: a weekly email to more than about 80 subscribers, or an invite burst, can use the whole daily Resend quota and block sign-in codes for the day. A script can burn the Geoapify credits; the form then falls back to plain text, so impact is low.
- Fix: add a global daily send counter that refuses non-essential mail first and always leaves headroom for sign-in codes; confirm the Resend plan; add a simple per-IP limit on `/api/address`.
- Effort: S to M.

## What breaks first under a traffic spike

In order, assuming the free plan limits (and what happens on Workers Paid in brackets):
1. **D1 rows read** (5M a day free): the home page costs 4,618 reads a hit and `/api/events` rebuilds cost 3,270 each per colo every 2 minutes; crawlers already use 1.3M to 3.3M a day. When it trips, D1 errors and the map loads no events after the stale copy expires. [Paid: cost only.]
2. **Function invocations** (100,000 a day free): about 7 per visit, so about 14,000 visits a day. [Paid: 10M a month included.]
3. **CPU time per request** (10 ms free): p50 is already 14 ms and p99 94 ms, which is why the account is believed to be on Paid. If it is free, those requests would already be failing; they are not.
4. **Resend** (100 emails a day on free): shared by sign-in codes and all notices.
5. **Geoapify** (3,000 credits a day): address autocomplete degrades to plain text.
6. **D1 query concurrency**: one slow query is 75 ms for the events list, so a burst of cache misses queues. The stale-while-revalidate copy hides this for 15 minutes.
Not a concern now: R2 operations (24 photo keys referenced, static photo serving, backups of a few MB), Pages bandwidth (unmetered), GitHub Actions minutes (public repo), file count and file size limits (571 files, largest 19.1 MiB).

## Method notes and limits

- The Cloudflare token injected by the proxy allowed read access to Pages, D1 (`SELECT` through the query API), R2 bucket settings, and GraphQL analytics. It could not read subscriptions, so the plan is inferred, not read.
- I did not download the real backup or the live export link. The restore dry run used a database built from the repository's migrations.
- `gh` is not authenticated for Actions; run history came from the GitHub MCP tools.
- Preview configuration was read from the Pages API as of 2026-11-06 11:00 UTC.
- Not verified: Time Travel retention, the Resend plan, the Cloudflare plan, whether the Cache API serves on `*.pages.dev` hosts (the uptime check hits those).
